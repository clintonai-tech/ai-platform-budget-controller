# Task 2 Implementation Plan: Budget Controller

## Selected Option

Choose **Option B: Tiered budget enforcement with graceful downgrade**.

This is the strongest fit for the assignment because it combines Python implementation, the provided spend data, LiteLLM platform governance, and practical production tradeoffs. It also creates a good interview story: the component sits between spend telemetry and gateway enforcement, helping teams control cost without treating all workloads the same.

## QA Findings From Planning

- A dry-run controller is acceptable for version 1 only if it emits concrete LiteLLM-compatible policy intent and has a clear future `--apply` extension point.
- `uv.lock` should be generated by `uv` after dependencies are added, then committed.
- `.env` must never be committed. Commit only `.env.example`.
- Terraform should not be overbuilt for Task 2. Option B should remain Python-first, with Terraform described as future production deployment work.
- Policy actions should be formal enum values, not free-form prose.
- Spend freshness should be visible in decisions because budget data is naturally stale.
- Missing team ownership should be treated as a first-class governance violation.
- Tests should use small deterministic fixtures instead of the full assignment CSV for every case.

## Goal

Build a Python CLI package named `budget-controller`.

The component implements the policy brain of tiered budget enforcement. It reads spend data and declarative budget policy, evaluates budget thresholds, and emits deterministic enforcement decisions that could later be applied to LiteLLM.

The chosen implementation approach is a periodic controller: a worker reads accumulated spend from a source of record, evaluates policy, and pushes or exports gateway policy intent. In this take-home version, the source is the provided CSV. In production, the same decision engine would read from LiteLLM/Postgres and update LiteLLM policy through an admin API or generated config.

Version 1 is intentionally scoped:

- No live LiteLLM mutation.
- No AWS calls.
- No Datadog emission.
- Clean models, tested policy logic, structured output, and clear integration boundaries.

## Option B Questions Addressed

- Accumulated team spend: aggregate spend by team, API key, and model from the provided CSV.
- Tiered thresholds: evaluate 75%, 90%, and 100% budget thresholds deterministically.
- Warnings: produce structured warning and urgent-warning decisions before enforcement.
- Downgrade at 100%: produce gateway-intent output to route eligible workloads to cheaper models.
- Application signal: include explicit downgrade metadata in decisions so applications can show or handle the downgrade.
- Silent downgrade suitability: encode workload-specific downgrade policy for AdvisorChat, KYC, DevAgent, DigestBot, Research, and Marketing.
- Spend staleness: include `as_of` and freshness metadata in decisions, with conservative behavior when data is stale.
- Gateway update path: emit LiteLLM-compatible policy intent without requiring a live proxy in version 1.

## Capabilities Not Touched In Version 1

- No hot-path pre-call callback enforcement.
- No live LiteLLM admin API mutation by default.
- No real provider calls or model API keys.
- No real Postgres integration.
- No Datadog metric emission.
- No Terraform deployment.
- No AWS Lambda, ECS scheduled task, or EventBridge runner.
- No Slack, email, or ticketing notifications.
- No spend forecasting.
- No per-request estimated-cost blocking.
- No AWS CUR/provider invoice reconciliation.

## Definition Of Done

- A reviewer can run the project locally with `uv`.
- The CLI evaluates the provided spend CSV against a budget policy.
- The output shows team spend, threshold status, governance violations, and recommended LiteLLM actions.
- Tests cover normal behavior and edge cases.
- README explains architecture, assumptions, commands, and production integration path.
- No secrets, generated caches, or local virtualenv files are committed.

## Recommended Dependencies

Use `uv` for project and dependency management.

Runtime dependencies:

- `pydantic`: validation for policy config and decision models.
- `pyyaml`: YAML policy loading.
- `typer`: CLI interface.

Development dependencies:

- `pytest`: tests.
- `ruff`: linting and formatting. This is the only static-analysis gate; no
  separate type checker is used.

Avoid `pandas` in version 1. The CSV format is simple enough for Python's standard `csv` module, which keeps the component easy to audit.

## Dependency Timing

Do not install dependencies until Ticket 1 starts.

When implementation begins:

1. Initialize the project with `uv`.
2. Add runtime and dev dependencies.
3. Let `uv` generate `uv.lock`.
4. Commit the scaffold before implementing business logic.

## Ticket 1: Project Scaffold

Outcome: clean Python project foundation.

Acceptance criteria:

- `uv` project initialized with `src/` layout.
- `pyproject.toml` defines package metadata, Python version, pytest, and ruff settings.
- Runtime dependencies are added: `pydantic`, `pyyaml`, `typer`.
- Dev dependencies are added: `pytest`, `ruff`.
- `.gitignore` excludes `.env`, `.venv`, caches, coverage, dist, and build output.
- `.env.example` includes future variables such as `LITELLM_BASE_URL` and `LITELLM_API_KEY`.
- `README.md` has setup commands and project purpose.

## Ticket 2: Data And Config

Outcome: input files are present and documented.

Acceptance criteria:

- Assignment CSV is copied to `data/spend_30d.csv`.
- `config/budget_policy.yaml` defines each team, monthly budget, thresholds, default action, downgrade model, and enforcement mode.
- Thresholds are explicit: `0.75`, `0.90`, `1.00`.
- Actions are enum-like: `allow`, `warn`, `urgent_warn`, `downgrade`, `throttle`, `block`, `require_explicit_signal`, `quarantine`.
- README documents that spend data is treated as near-real-time sample input.

## Ticket 3: Domain Models

Outcome: policy, spend rows, aggregates, and decisions are typed.

Acceptance criteria:

- Pydantic models validate policy config.
- Invalid thresholds, unknown actions, missing budgets, and duplicate team names fail clearly.
- Decision model includes `team`, `budget_usd`, `spend_usd`, `percent_used`, `status`, `action`, `reason`, `as_of`, and `data_quality_flags`.
- Tests cover valid and invalid config.

## Ticket 4: Spend Loader

Outcome: CSV parsing is safe and auditable.

Acceptance criteria:

- Loader parses date, API key, team, model, request count, token counts, and cost.
- Blank or invalid `cost_usd` is recorded as a data quality issue.
- Missing team is recorded as a governance violation.
- Zero-request nonzero-cost rows are preserved and flagged.
- Aggregation works by team, API key, and model.
- Tests use small fixtures and cover malformed rows.

## Ticket 5: Policy Evaluator

Outcome: threshold decisions are correct and deterministic.

Acceptance criteria:

- Below 75% returns `allow`.
- 75%-89.99% returns `warn`.
- 90%-99.99% returns `urgent_warn`.
- At or above 100% returns the configured enforcement action.
- Missing team ownership returns `quarantine` or `block`.
- AdvisorChat and KYC never silently downgrade.
- DigestBot and Marketing may downgrade.
- Research may throttle or downgrade.
- DevAgent downgrade is allowed only for non-write workloads if modeled in config.
- Boundary tests cover exactly 75%, 90%, and 100%.

## Ticket 6: LiteLLM Exporter

Outcome: decisions become actionable gateway-intent output.

Acceptance criteria:

- Exporter produces JSON representing intended LiteLLM policy changes.
- Example outputs include model alias downgrade, RPM/TPM reduction, key block, team warning, or explicit downgrade signal.
- Export format is stable and documented.
- No live LiteLLM API calls in version 1.
- Tests snapshot or assert the generated JSON structure.

## Ticket 7: CLI

Outcome: reviewer can run the component easily.

Acceptance criteria:

- Command works: `budget-controller evaluate --spend data/spend_30d.csv --policy config/budget_policy.yaml`.
- Supports `--format table` and `--format json`.
- Supports `--export-litellm`.
- Invalid config or missing file exits nonzero.
- Over-budget teams do not crash the program; they produce enforcement decisions.
- CLI tests cover success and failure paths.

## Ticket 8: README And Review Polish

Outcome: the submission explains both the code and platform relevance.

Acceptance criteria:

- README explains why Option B was chosen.
- README includes architecture flow: CSV/Postgres spend source -> budget controller -> decisions -> LiteLLM policy update -> Datadog alerts later.
- README includes local setup, test, lint, and run commands.
